# 第一轮可靠性优化：验证与上线

2026-10-16 已与暖白手记 UI 一同部署到生产，013—015 增量已执行。上线版本、备份路径和无副作用验收结果见 `PROGRESS.md` 的“暖白手记与 M14 上线完成”；真实短信发送、生产上传转码和故障演练不在本次验收范围。

## 行为变化

### 上传归属

- 预签名时把对象名、上传者、用途、声明类型与大小上限写入 `storage_upload`。
- 创建作品、更新头像、评论/回复图片、私信图片都校验登记归属、用途及存储元数据；不能提交其他账号的对象名或任意外部 URL。
- 视频上限 500 MiB，图片/封面上限 20 MiB；这是业务绑定时的校验，不是上传过程中实时拦截体积。
- 删除先锁定登记行，检查作品、头像、评论和私信的引用；确认无人使用后，事务提交再删除对象。转码成品也登记归属。
- 已有完整 URL 继续可读；未变更的历史头像不要求重新上传。普通图片不压缩，HEIC/HEIF 仅为浏览器兼容转换 JPEG。
- 校验主要依据对象存储元数据；它不是完整的文件内容安全扫描，也没有加入未绑定上传的自动过期清理。

### 登录续期

- 浏览器保存访问令牌与刷新令牌；接口返回 401 时，并发请求共享一次刷新，成功后每个原请求最多重试一次。
- 无效或过期刷新令牌返回 HTTP 401，清理登录状态并保留安全的站内回跳地址。
- 网络错误或服务端故障不直接注销账号；登出或切换账号后，旧刷新结果不能恢复旧登录。
- WebSocket 随访问令牌轮换重连。首次升级后，旧版本已登录但没保存刷新令牌的浏览器可能需要重新登录一次。
- 发布/评论草稿并未全部持久化；令牌仍存储于 localStorage，HTTPS、XSS 防护和多设备令牌撤销仍需单独建设。

### 点赞/播放量缓冲

- Redis Lua 把有限数量的 pending 项原子移入 inflight，并保留稳定批次号。
- 批次回执与所有 MySQL 增量在同一事务提交；成功后才 ACK Redis。重复执行同一批次不会重复累加。
- 数据库故障、提交后未 ACK、阶段响应丢失等情况下，下次定时刷新继续处理保留的批次。读取时排除已落库但尚未 ACK 的 inflight 增量。
- 这是最终一致的展示计数，不是跨 Redis/MySQL 的强一致事务。关系表写入到 Redis 记录增量之间仍有故障窗口；Redis 自身未持久化的数据丢失也不在本轮恢复保证内。
- `counter_batch_receipt` 不可随意清空，否则遗留批次可能被重复应用。点赞关系表仍可作为人工核对依据。

### 视频转码

- 视频作品和 `transcode_task` 在同一数据库事务登记；提交后投递 RabbitMQ 并等待 publisher confirm，同时检查不可路由返回。
- 消息投递失败转为待补偿；每 30 秒扫描到期任务。已投递但无人认领的任务，30 分钟后可以重新投递。
- 工作进程使用唯一租约认领任务；租期 120 秒，每 15 秒续租。过期任务重新排队，旧租约不能覆盖新任务结果。
- 单次任务最多自动处理 3 次，失败间隔至少 30 秒；达到上限才把作品标记 FAILED，保留源视频供作者重新处理。
- 作者可在发布失败面板或作品设置选择“重新处理视频”，调用 `POST /api/posts/{id}/retry-transcode`，不必重新上传源视频。源文件已不存在时需重新上传。
- 任务完成与作品发布同事务提交；成功后才清理仍属于作者且没有其他有效引用的源文件。状态提交结果不确定时保留产物，避免误删已发布视频，因此极端故障下仍可能留下孤儿文件。

## 数据库升级

先备份数据库及现有应用产物，暂停旧版应用写入。已有 001—012 的库按顺序执行：

1. `db/init/013_m14_upload_ownership.sql`：登记上传归属，并回填符合旧 UUID 命名规则且引用者唯一的历史对象。
2. `db/init/014_m14_counter_recovery.sql`：建立计数批次回执表。
3. `db/init/015_m14_transcode_recovery.sql`：建立转码任务表，为现有 PROCESSING 视频补任务。

013 的回填根据业务引用推断归属，并非原始上传审计证明；正式执行前需审查候选记录。冲突归属、任意旧 key 和完整 URL 不授予新绑定/删除权限。无法确认归属时宁可保留文件，不做猜测删除。

脚本新增表且支持重复执行，但不应把整套历史脚本在生产库盲目重放。新后端依赖三个新增表，不能先换 jar 后补 SQL。

## 上线顺序

1. 保存旧 jar、前端 dist 与数据库备份；确认 Redis 持久化和 RabbitMQ 正常。
2. 在维护窗口停止旧后端，执行并核验三个增量脚本；不要清空 Redis pending。
3. 更换后端产物并启动，确认无缺表错误、定时补偿正常，再更换前端 dist。
4. 验证登录/续期、作品/头像/评论/私信上传、发布与删除，以及作者失败重试入口。
5. 检查旧头像、旧作品仍可读取；用测试账号验证跨账号对象引用被拒绝，不使用真实用户数据进行故障注入。
6. 观察 `journalctl -u shiguang` 或应用日志，以及下方只读状态查询。

```sql
SELECT state, COUNT(*) FROM transcode_task GROUP BY state;
SELECT post_id, attempts, last_error, next_attempt_at
FROM transcode_task WHERE state IN ('PENDING', 'FAILED')
ORDER BY updated_at DESC LIMIT 20;
SELECT counter_name, COUNT(*) FROM counter_batch_receipt GROUP BY counter_name;
```

Redis 可查看 `HLEN like:pending`、`HLEN view:pending` 及各自 `:inflight`、`:batch`，排查是否长期堆积。不要直接删除 inflight/批次号来“解锁”。

## 回滚边界

- 三个新增表先保留，不执行 DROP；数据库备份与 Redis 备份需要配套保留。
- 旧版本不知道 inflight。若必须回滚，先暂停业务写入，使用新版本排空 pending/inflight 并核对计数，再停服务更换旧产物；不能带着未处理批次直接降级。
- 正在处理的视频先等待完成或记录任务状态，不能让新旧消费者同时运行。生产转码和 OSS 删除不可用恢复数据库来撤销。
- 归属登记会保护旧版无法识别的历史文件；回退后安全校验也会回退，应尽快恢复新版本。

## 本地验证命令

需要 JDK 21、测试数据库、Redis 与 RabbitMQ；不要把生产连接参数带入集成测试。

```powershell
.\mvnw.cmd test
cd frontend
node --test tests/auth.test.mjs
npm run build
```

本机全局 Maven 指向不可达的公司仓库时，可执行 `.\mvnw.cmd -s .devtools\maven-settings-public.xml test`，使用仓库附带的公共仓库设置。
